** RESOLVED Additive post-start initialization with static tools
:PROPERTIES:
:ID: ssh-injection-additive-init
:SOURCE: user
:END:
Implemented after the user's authorization: a static Go initializer embeds a compressed amd64 static musl tool payload. Kubernetes exec uploads the initializer and passes lease ID, public key and expected host key/port as JSON stdin. The client private key stays local; the daemon host private key stays remote. Three exact response markers convey the SSH user, host public key and dynamically selected loopback port for identity pinning.

The initializer verifies root, architecture, existing root/login-shell compatibility and trusted writable paths. It stages a content-addressed runtime under =/opt/crabbox-runtime=, probes existing tools, and creates only missing compatible aliases. Incompatible existing tools cause rejection, not replacement or PATH shadowing. It never edits =/etc/passwd=, =/etc/shadow=, =/etc/group= or =/etc/shells=. Root and the small existing =uname/sh/mkdir/cat/chmod/rm/rmdir= delivery foothold remain required.

A bundled Dropbear 2026.94 daemon uses private authorization, host key, PID and log state under =/var/lib/crabbox-ssh/<lease-id>= and an available loopback port. Normal upstream multiuser support is retained: disabling it requires a kernel built without multiuser support and is not a root-only authentication mode. Password/PAM login is disabled; public-key login works with a locked root password without changing account files. A narrow root-shell policy patch removes dependence on the system shell allowlist, not authentication. Dropbear's configured default PATH preserves the inherited image PATH. Core's existing login-shell semantics are unchanged.

Repeated initialization verifies the runtime and daemon identity and retains the pinned host key and port. The entire initializer is uploaded even on reuse; only missing tools are added. The final uploaded ELF is 36,221,054 bytes; its embedded gzip is 33,428,022 bytes. No incremental initializer-transfer optimization is implemented.

** RESOLVED Forward input only to the actual POSIX SSH workload
:PROPERTIES:
:ID: ssh-injection-workload-stdin-fix
:SOURCE: user
:END:
Live tests exposed that ordinary =run= and =--script= discarded piped input: their streaming helper always passed nil and selected SSH =-n=. The user authorized fixing discovered bugs. POSIX SSH workload dispatch now passes the borrowed application input explicitly; sync, script upload, probes and ownership commands retain separate or nil input. =--script-stdin= still consumes source without replaying it as runtime data. Windows/native-WSL and provider-native delegated input behavior remain unchanged. Live input is not replayed after ambiguous transport or multiplexing failure.

The implementation preserves borrowed input ownership and closes its own pipe descriptors. Focused review found an avoidable prelaunch pipe leak/premature Read; copying now begins only after successful process start, and repeated failed diagnostic/exec launches prove zero reads and no descriptor growth. An arbitrary borrowed reader already blocked in Read cannot be forcibly canceled without taking ownership; the command returns without waiting for that reader and closes only its owned pipe. The final source passed the SSH/workspace-owner regression selection, live matrix, scoped go vet, Windows test-binary cross-compilation, and race-enabled stdin regression cases. Source review reports no outstanding actionable findings. No full-repository or live-Windows pass is claimed.

** PARKED Ship a tool bundle through a shared volume
:PROPERTIES:
:ID: ssh-injection-shared-volume
:SOURCE: user
:END:
The user asks whether "a sidecar volume or smth" can provide the tools. Kubernetes init containers can populate an emptyDir before the workload starts, and the workload can mount that bundle read-only at a fixed private path. This needs Pod/template configuration but not an application-image rebuild or a persistent copying sidecar. An SSH server running only in a sidecar would execute workloads in the wrong container by default; a shared workspace alone does not transfer the application's root filesystem or environment. Proposed direction to prototype: ship a self-contained runtime bundle through an init container, launch its established SSH server in the workload container, and use explicit individual subPath compatibility mounts for required absolute tool paths. Do not mount over entire /bin or /usr/bin directories. The mounts can replace visible tools and must be intentional; merged-/usr layouts, existing symlinks, library/loader dependencies, Git subprocesses, executable-volume policy and SSH account/UID requirements need verification. A volume supplies files, not binary portability or account compatibility. The user now asks, "does agent-sandbox expose init container? idk if a initcontainer + volume is really nice. How involved is the container setup?" This questions operational complexity rather than accepting the volume design. Upstream docs/api.md establishes SandboxTemplate.spec.podTemplate.spec as a full Kubernetes PodSpec, so initContainers, volumes and volumeMounts are available. SandboxWarmPool refers to that template. Current Crabbox only submits warmPoolRef and lifecycle in its claim, so the operator must configure the template before pool Pods exist; there is no claim-level init-container injection hook here. The simple copy-volume part is routine, but the full SSH and compatibility-mount integration is a nontrivial template addition. The proposal remains under review, not implemented or proven.

The user has now proposed copying and running an additive initializer after startup instead. That avoids template mount changes on supported writable containers, so the volume approach remains an alternative under review rather than the active recommendation.
